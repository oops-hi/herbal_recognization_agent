# 多模态中草药识别智能体 · 二期升级实施方案

（对齐《项目立项报告（调研增强版）》14 章结构；升级聚焦：**知识侧 + 智能体侧**）

- 项目定位：中药材识别 + 多模态知识增强 + 安全可控智能体
- 一期（V1，已完成）：20 类 yolo8n-cls 识别 + 知识图谱 + 手写 ReAct 智能体 + Web/桌面双端
- 二期（V2，本方案）：知识底座升级（药典对齐 + 版本化溯源 + 混合检索）＋ 任务型多智能体编排（五道安全闸门 + 证据链拒识）
- 报告用途：二期研发排期、资源申请与验收依据

## 一、项目摘要与立项结论

### 1.1 一期成果回顾（V1 已完成，实测数据）

本项目一期已经跑通「看图识药 → 知识问答 → 安全约束 → 桌面交付」的完整 MVP：

| 模块 | 一期实现 | 实测结果 |
|---|---|---|
| 图像识别 | yolo8n-cls，20 类果实种子类饮片（NB-TCM-CHM，3,784 张） | 同域 val top-1 **93.8%** / top-5 99.7%；跨域药房实拍 test top-1 **85.75%** / top-3 96.75% |
| 知识图谱 | NetworkX + 单文件 kg.json：22 味带档案药材（20 主药 + 菊花/甘草）、10 禁忌网络节点、45 方剂组成节点、12 首经典方剂 | 84 节点 / 84 边；9 条禁忌边（双向去重），歌诀 + 药典双源字段 |
| 智能体 | 手写 ReAct 循环（不用 LangChain），6 个工具 + JSON Schema + REGISTRY 白名单 | 真实链路：枸杞子×菊花 4 次工具调用 + 杞菊地黄丸 ✅；瓜蒌皮×川乌 3 次调用 + 十八反双源 ✅ |
| 安全与合规 | 低置信度拒识（阈值 0.75）、断网 fail-soft、溯源字段、免责声明面板 | 演示脚本 7 步验收全过；宠物照片正确拒答 + 补拍建议 |
| 交付形态 | Flask Web + Vue3 桌面版（Electron + NSIS 安装包） | 安装包已产出（1.93GB）；装机验证为唯一待办 |

### 1.2 立项结论：建议立项二期，聚焦"知识打底、智能体塑形"

对照《项目立项报告（调研增强版）》的 R01–R12 需求清单，一期已覆盖其中一部分（识别、置信度拒识、知识溯源、安全护栏、合规边界），但**知识底座仍偏薄、智能体仍是单循环**。二期不追求"更大的模型"，而是把一期已经验证的"识别 + 问答 + 安全"闭环，从**演示级升级为可扩展、可审计、可评测**的产品级能力：

- **知识打底**：图谱档案从 22 味扩展到 60+ 味，对齐《中国药典》，新增 L1 性状/鉴别字段与 L2 药典原文字段，建立版本化台账与混合检索（图谱精确检索 + 向量模糊召回）。
  - 📌 **P0 落地口径（2026-08-28 用户拍板）**：L2 原文口径维持《中国药典》2020 年版一部（与一期核对基准一致）；2025 版切换依赖 `source_edition` + review_ledger 台账批量重核机制，不作为 P0 数据口径。
- **智能体塑形**：从单一 ReAct 循环升级为**任务型多智能体编排**（识药/鉴别/药性/方剂/安全/学习），落地立项报告的"五道安全闸门"与证据链拒识（refuse_reason 结构化）。
- **明确不做**：自动生成处方、个体化诊疗建议、真伪与产地判定——沿用一期合规红线，二期不变。

## 二、行业与技术调研

### 2.1 政策与产业环境（沿用立项报告结论）

政策方向明确支持，且对安全可控的要求在提高：

- 国务院办公厅《中医药振兴发展重大工程实施方案》明确提出构建中药质量信息数据标准和统计体系，开展中药品质智能辨识与控制工程化技术装备研究 [3]。
- 2024 年国家中医药管理局、国家数据局推进"数字中医药"，要求中医药数据分类分级管理与多源数据融合标准规范 [4]。
- **2025 年《人工智能+医疗卫生》政策**进一步强化"创新应用 + 安全可控"并行，要求风险分级、人工复核和可追溯机制 [5]——这正是本项目一期已建、二期要加强的设计方向。

### 2.2 图像识别研究现状（与本项目一期实测对照）

| 公开研究/资源 | 规模 | 报告精度 | 对本项目的启示（已在一期验证） |
|---|---|---|---|
| NB-TCM-CHM（本项目数据源） | 20 类；3,384 网络图 + 400 手机实拍 | 数据集原论文协议 | 跨域（网络→药房实拍）确实掉点：本项目 val 93.8% → 跨域 85.75%，证实"基础模型不是瓶颈，泛化验证更重要" |
| 163 类中药材 CNN 研究 | 276,767 张 | EfficientNet-B0 约 99.0% | 大模型在实验室分布上很强，但需真实场景验证 |
| Herb-LT / PT-Herb（2026） | 180 类、长尾分布 | — | 类别规模从几十扩到数百时，长尾与细粒度成为核心挑战；二期识别侧不动，恰是回避该问题的务实取舍 |

**本项目一期实测的"已知弱点"即为二期知识侧要补的洞**：桃仁 recall 仅 0.30（14/20 误判，主要流向苦杏仁/川楝子）、草豆蔻 recall 0.45（8 张误判为砂仁）、砂仁/川楝子 precision 偏低（0.59/0.61）。这些**外观相似导致的误识，单靠分类模型难以根治**，立项报告给出的方向是"Top-K + 拒识 + 相似鉴别"，而相似鉴别需要**细粒度知识支撑**（性状、纹理、切面特征）——二期知识侧 L1 字段（性状/鉴别要点/similar_herbs 相似对）正是把知识接到这个洞上：识别不敢断言时，智能体可以"给出候选 + 鉴别要点对比"，而不是硬猜。识别模型本身的改进（类加权/更高 imgsz/延长训练）列入后续。

### 2.3 知识图谱 + RAG + 多智能体方向（二期技术依据）

- 立项报告引用的药用植物多模态知识图谱研究（340,772 实体 / 2,530,067 关系）表明"识别 + 图谱 + 问答"路线可行，但其识别准确率约 83.53%，再次说明**"识别模型"与"知识服务"必须分层建设，识别置信度不等于知识答案可靠度** [9]——本项目一期即按此分层。
- **GraphRAG 定位（本项目既有结论，见需求分析 §11.3）**：禁忌/配伍/方剂组成是**精确关系检索**，图谱遍历是"命中"，向量 top-k 是"相似"，相似即猜测，与"药典为准、禁止凭记忆补充"的合规红线冲突。因此二期的知识底座采用**混合架构**：图谱负责精确关系（主治、禁忌、组成），向量检索只负责**非结构化文档的候选召回**（如古籍、药典凡例、教学材料），且召回的每条证据必须带 source 才能进回答。
- **多智能体编排（二期新增）**：立项报告第八章提出"不要把一个大模型直接包成聊天机器人，而应设计为任务型智能体"。一期已证明单 ReAct 循环可行（工具调用链由问题决定），二期将其扩展为**分工明确的多智能体**：每个子智能体拥有自己的工具集与职责边界，编排层只做意图路由与汇总——仍保持手写、不引入 LangChain（与一期技术路线一致，规避框架黑盒与依赖风险）。

| 技术方向 | 对本项目二期适用性 |
|---|---|
| 图谱精确检索（已有） | 直接沿用：禁忌/组成/方剂精确命中，亚毫秒 |
| 向量 RAG（新增） | 仅作非结构化文档候选召回，证据必须带 source，图谱终审 |
| 多智能体编排（新增） | 一期 ReAct 已验证工具调用链，二期按职责分组 + 轻量路由 |

### 3.3 进一步建议：把"问答"升级为"证据链"

立项报告 3.2 建议把"识别"从单分类升级为"证据链"。本项目一期已在识别侧实现了"候选 Top-K（内部）→ 低置信度拒识 → 补拍建议"的链条；二期把同一思想**移植到问答侧**：

1. **问题意图判定**：路由到对应子 Agent（药性 / 禁忌 / 方剂 / 相似鉴别）；
2. **候选证据召回**：图谱精确命中 + 文档向量召回，**只召回带 source 的证据**；
3. **知识校验**：候选证据与问题实体的映射校验（别名索引，kg/query.py 既有 `_resolve_or_unknown`）；
4. **安全判定**：命中高风险主题（十八反/十九畏、特殊人群、剂量询问）→ 业务闸门模板；
5. **答案生成**：只允许 LLM 在召回证据范围内组织答案，逐条附来源与版本；
6. **拒识兜底**：任一环节证据不足 → 明确拒答并给出 refuse_reason，**宁可拒答也不硬猜**。

## 四、产品定位与核心应用场景

### 4.1 定位（不变）

**辅助学习与知识查询工具，不是医疗决策工具。** 面向中药学学生、调剂员与养生人群，提供"看图识药 + 药性知识问答 + 安全提示"的可靠助手；诊断、辨证、剂量、疗效结论**一律不输出**。

### 4.2 二期核心场景

| 场景 | 目标用户 | 核心能力 | 风险等级 | 二期建议 |
|---|---|---|---|---|
| 拍照识药 | 普通用户/学生 | 图片上传、Top-K 识别、基础介绍 | 中 | 保持（一期已交付） |
| 药材鉴别辅助 | 药师/中药房 | 相似药材对比（L1 知识）、证据链 | 高 | **重点做**：鉴别子 Agent + 相似对知识 |
| 中医药知识问答 | 医生/研究/教学 | 图片+文本问答、图谱、药典原文、文献召回 | 中高 | **重点做**：药性/方剂子 Agent + 混合检索 |
| 茶饮配伍问答 | 养生人群 | 药性档案 + 禁忌双源 + 方剂示例 | 中 | 新增：低风险场景，与"眼睛干→杞菊地黄丸"用例同链路 |
| 药材市场真伪初筛 | 市场/个人 | 真伪判断 | 极高 | 不做（超出合规红线与数据能力，明确列入"不做"） |
| 经典方剂检索 | 医生/研究者 | 证候/药材 → 经典方候选匹配 | 高 | 受控做（候选/经典方，不生成处方） |
| 处方建议 | 临床 | 结合患者信息生成处方 | 极高 | **一期不做，二期仍不做** |

**产品边界原则（沿用立项报告）**："识别"可以做成产品能力，"诊断/处方"必须做成受控能力。二期在 UI、接口、日志和模型策略上继续把两者区分开。

### 5.4 技术选型说明

- **向量库**：chromadb（本地文件式，无外部服务）+ `bge-small-zh` embedding（本地运行，约 100MB 模型）。选型理由：与项目"0 外部请求、断网可用"的既有约束一致（前端 0 CDN、后端断网 fail-soft）；规模小（60+ 味 + 若干文档），无需 PGVector/Elasticsearch。
- **图谱**：继续 NetworkX + JSON（一期已论证毫秒级响应，200+ 味仍无压力；kg.json 200+ 味时改程序化导入，后端可替换 SQLite/Neo4j 不影响接口——见需求分析 §11.4）。
- **不引入**：LangChain（编排手写，一期已验证）、PostgreSQL（当前规模 JSON+缓存足够）、云端 LLM 以外的任何在线服务。
- **知识侧总原则**："**图谱给准确，RAG 给全面**"——禁忌/组成/方剂等高风险结论只信图谱精确命中；RAG 只补充图谱未覆盖的开放问题，且召回证据无 source 则丢弃。
- **云端 VLM（可选增强，V2-A6）**：独立 VISION 配置与 DeepSeek 文本配置并存——**DeepSeek 聊天 + 可插拔视觉供应商**（如硅基流动 deepseek-vl2、智谱 GLM-4V、通义 Qwen-VL，均为 OpenAI 兼容 /chat/completions）。定位一句话："**本地快、云端准、只在灰区才问云端**"——识别侧本地模型高置信时零云端开销，灰区（低置信/混淆对/候选差距小）才触发 VLM 交叉验证，断网/超时自动跳过，默认开关关闭。

## 六、知识库与安全体系设计

### 6.1 知识源分级（对齐立项报告，含 2025 药典）

| 等级 | 知识来源 | 用途 | 约束 |
|---|---|---|---|
| A | **2025 年版《中国药典》**及正式药品标准 | 标准品种、性状、鉴别、炮制、性味归经、用量 | 最高优先级；版本化管理，二期 L2 原文照录目标 |
| A | 国家药监、国家中医药局等公开资料 | 监管、质量、政策、标准 | 保留原文链接/发布日期 |
| B | 权威教材、行业规范、专业数据库 | 知识补充、教学解释 | 记录来源与版本 |
| C | 高质量论文/研究成果 | 科研知识、算法与证据 | 不可自动升格为临床结论 |
| D | 互联网百科/社区内容 | 仅作线索 | **不得作为任何回答的证据**；二期明确禁止进入 RAG 语料 |

> **版本切换机制（二期必建）**：2025 年版《中国药典》已于 2025-10-01 施行（2025 年第 29 号公告）[1][2]。二期知识条目的 L2 原文字段统一标注 `source_edition`；版本台账记录"条目 × 药典版本 × 核对状态"，未来药典更新时按台账批量重核，杜绝"新药典生效、旧数据继续答"。
>
> 📌 **P0 落地口径（2026-08-28 用户拍板）**：L2 数据口径维持《中国药典》2020 年版一部，`source_edition` 统一为 `"《中国药典》2020 年版一部"`（与一期已核对的 24 味基准一致）；2025 版差异不在 P0 起草，切换时走本台账机制批量重核。

### 6.2 五道安全闸门：现状与二期补强

| 闸门 | 拦截位置 | 一期现有实现 | 二期补强 |
|---|---|---|---|
| ① 输入闸门 | 上传入口 | 扩展名 + 16MB 校验；低置信度补拍建议文案 | 保持；refuse_reason=域外图 时返回"补拍建议 + 四类原因"结构化；**可选增强**：VLM open-set 域外判定（判 non_herb → 域外图拒答，补强一期宠物图高置信误判 0.94 的漏洞） |
| ② 识别闸门 | 识别层 | Top-1 < 0.75 拒答（含调优记录） | 保持阈值；输出候选 Top-K 供鉴别子 Agent 使用；**可选增强**：灰区（0.60 ≤ Top-1 < 0.90 / 命中混淆对 / Top-1−Top-2 < 0.05）触发 VLM 交叉验证 |
| ③ 知识闸门 | 知识检索 | source 字段 + 白名单（未收录药材拒答） | 混合检索只放行带 source 的证据；无证据即拒答 |
| ④ 业务闸门 | 编排层 | 合规 System Prompt：不输出诊断/剂量/疗效 | 模板化：剂量询问 → 知识条目展示（非"你应该用 X 克"）；高风险主题 → 受控回答模板 |
| ⑤ 输出闸门 | 回答出口 | 强制溯源 + 免责声明面板 | 证据链明细（每条回答附来源与版本）+ refuse_reason 全量结构化 |

**refuse_reason 四类（二期新增结构化字段）**：

| 拒识原因 | 触发条件 | 系统动作 |
|---|---|---|
| `知识缺口` | 问题实体不在知识库（60+ 味之外） | 明确告知未收录 + 建议联系人工核对 |
| `置信不足` | Top-1 < 0.75 或候选差距过小 | 补拍建议（光照/背景/特写） |
| `域外图` | 非药材图像（宠物等） | 拒答 + 说明系统边界 |
| `合规边界` | 涉及诊断/剂量/疗效/真伪/产地 | 合规提示 + 免责声明 + 引导到受控回答 |

## 七、数据工程与模型训练

### 7.1 二期数据工程原则

- **识别侧不动**：一期不重训分类模型。类别扩充（20 → 100+）、TCMP-300 跨数据集增强、主体定位框（需求分析 §11.2，状态：待实施）全部列入**三期/后续**——识别侧扩类需要数据集与重训，是"重活"，与二期知识侧解耦。
- **知识侧为主**：二期数据工程 = 知识条目建设 + 人工核对流程，核心资产是**经过核对、带版本、可追溯的知识台账**，不是更多图片。

### 7.2 知识条目建设流程（二期主线）

```
白名单扩充（22 → 60+ 味，按药典收录排序）
   → L1 字段初稿（性状/炮制/产地/鉴别要点，来自药典与教材）
   → L2 药典原文摘录（性味归经/功效/主治/用法用量，逐字照录）
   → 人工逐条核对（沿用一期 review_items 核对清单流程）
   → 标记 reviewed_by / review_date / version → 进版本台账
   → kg.json schema_version=2 冻结，查询层零改动兼容
```

**红线（沿用一期）**：全部药性/方剂/禁忌条目必须以《中国药典》为准并带 `source` 字段；**LLM 起草 ≠ 定稿**，人工逐条核对；不加无药典来源的偏方/食疗功效/网络科普（需求分析 §11.4 红线）。

### 7.3 模型与知识协同：跨域弱点的知识侧化解

一期已知弱点（桃仁 recall 0.30、草豆蔻 0.45、砂仁/川楝子 precision 偏低）在二期通过"识别结果 × 知识侧鉴别"协同化解：

- 识别输出 Top-K 候选 → 鉴别子 Agent 调 `similar_herbs` + `similar_compare`，输出**鉴别要点对比**（如"桃仁 vs 苦杏仁：桃仁表面黄棕色、有纵皱纹，苦杏仁表面黄棕色至深棕色、种皮薄"）——给用户判断依据，而不是二次硬猜；
- 高风险相似对（砂仁/豆蔻/草豆蔻、苦杏仁/桃仁、山楂/金樱子）在 L1 字段建 `similar_herbs` 索引，前端图谱页联动展示。

### 7.4 标注与数据台账（对齐立项报告 7.2 精神的最小实现）

| 项 | 二期落地 |
|---|---|
| 主标签 | 标准中药材名称 + 唯一 ID（沿用 class_map.json / kg.json 命名） |
| 知识证据 | 每条字段标注来源等级 A–D + source_edition + 核对状态 |
| 复核 | 高风险条目（禁忌/用量）双人复核（本人 + 导师/评审） |
| 台账 | kg.json `review_items` 升级为版本化台账（含核对日期、核对人、版本号） |

## 八、智能体设计：从单循环到任务型多智能体

### 8.1 总体思路（沿用立项报告第八章 + 一期已验证的 ReAct）

一期验证了"工具调用链由问题决定"的手写 ReAct 可行（不用 LangChain）；二期将其**按职责分组为六个子智能体**，编排层只做意图路由与结果汇总。每个子 Agent 仍是一个受限的 ReAct 循环（更小的工具集 + 更聚焦的 System Prompt），共享现有基础设施：REGISTRY 白名单、JSON Schema 入参校验、429 退避、断网 fail-soft、流式事件协议。

### 8.2 六子 Agent 能力表

| 子 Agent | 触发条件 | 工具集（来自/新增 tools.py） | 闸门 | 输出 |
|---|---|---|---|---|
| 识药 Agent | 用户上传图片 | recognize_herb（一期已有）+ **vlm_verify（新增，可选工具，默认关）** | 输入/识别 | 候选药材 + 置信度 + refuse_reason |
| 鉴别 Agent | 候选相似度高/用户问"和 X 怎么区分" | similar_herbs（已有）+ **similar_compare（新增）** | 识别/知识 | 差异点 + 结论等级（可判定/需人工） |
| 药性 Agent | 问功效/药性/配伍理由 | get_herb_profile（已有）+ **retrieve_doc（新增，RAG）** | 知识 | 结构化药性信息 + 逐条引用 |
| 方剂 Agent | 问配伍/经典方/症状找方 | formulas_by_herb / formulas_by_symptom（已有） | 业务 | 候选经典方 + 来源（不生成处方） |
| 安全 Agent | 涉及禁忌/剂量/人群 | check_compatibility（已有）+ 业务闸门模板 | 业务/输出 | 双源风险提示/拒答/转人工 |
| 学习 Agent | 用户/专家修正结果 | search_herbs（已有）+ 台账写入（新增） | — | 错误样例入核对队列 + 再训练/再核对任务 |

### 8.3 编排层（Router）设计要点

```
用户提问
  → Router：意图分类（一句话，可选 LLM 或规则兜底）
     - 含图片 → 识药 Agent（必要时级联鉴别 Agent）
     - 药性/功效 → 药性 Agent
     - 配伍/禁忌 → 安全 Agent → 方剂 Agent
     - "怎么区分/相似" → 鉴别 Agent
     - 含修正信息 → 学习 Agent
     - 无法分类 / 无证据 → 知识闸门拒答（refuse_reason=知识缺口）
  → 子 Agent 执行（受限 ReAct，工具调用链由问题决定——一期核心卖点保留）
  → 汇总层：证据链整理（每条结论附 source_edition）+ 合规检查
  → 输出闸门：SSE tool/answer 事件（协议不变）
```

**关键设计约束**：

1. **Router 快速失败**：意图不明确时优先转"人工引导式追问"，不无限嵌套子 Agent（规避多 Agent 级联复杂度风险）；
2. **配额制**：MAX_TURNS=8 改为按子 Agent 配额（如每子 Agent ≤ 4 轮），防止长链失控；
3. **证据链贯穿**：每个子 Agent 的每次工具调用都进入时间轴（前端已支持），最终回答必须逐条带来源；
4. **安全 Agent 最高优先级**：任何子 Agent 命中高风险主题，立即让位于安全 Agent 的受控模板；
5. **仍手写**：不引入 LangChain/Agent 框架，理由同一期——白名单校验、参数校验、异常回填自纠已自证可用，框架黑盒与依赖升级风险不值得引入。

### 8.4 混合检索接入（药性 Agent 与学习 Agent 的增强）

- 图谱未覆盖的开放问题（如"枸杞子对眼睛的作用原理"）→ `retrieve_doc` 走向量召回权威文档片段；
- 召回条件：**文档必须来自 data/tcm_docs/ 版本目录（A/B 级来源），哈希溯源，无 source 即丢弃**；
- 药典原文类问题直接命中 L2 字段（图谱路径），不经过向量——保证高风险结论走精确命中。

### 8.5 云端 VLM 辅助验证通道（V2-A6，可选增强）

**动机**：一期识别侧的两个已知漏洞单靠本地小模型无法根治——① 桃仁 recall 仅 0.30、草豆蔻 0.45 等**语义级相似混淆**（8n 分类器对纹理细节分辨力有限）；② 域外图**高置信误判**（宠物图误判最高 0.94，高于 0.75 阈值照样硬答，"高置信 ≠ 域内"）。云端 VLM（图文对齐 + 开放词表）恰好在这两个场景有互补优势，且工程接入成本低（一期 LLM 配置已是 OpenAI 兼容结构）。

**触发条件（灰区三条件任一，命中才调用云端）**：

| 触发条件 | 阈值 | 说明 |
|---|---|---|
| T1 低置信 | 0.60 ≤ Top-1 < 0.90 | 低于 0.60 直接拒答不走云端（省成本）；0.90+ 本地可信不打扰 |
| T2 高风险混淆对 | Top-1 命中桃仁/苦杏仁/川楝子、砂仁/豆蔻/草豆蔻、山楂/金樱子 | 命中一期已知弱类 |
| T3 候选差距小 | Top-1 − Top-2 < 0.05 | 候选近乎并列，需要第二证据 |

**决策矩阵（双通道）**：

| 本地（yolo8n-cls） | 云端 VLM 判定 | 系统动作 |
|---|---|---|
| 候选 A（灰区） | A | "双通道一致"提信，正常走知识问答 |
| 候选 A（灰区） | B（候选名单内另一味） | 级联**鉴别 Agent**：similar_herbs + similar_compare 输出鉴别要点对比，交用户判断，不硬猜 |
| 候选 A（灰区） | non_herb（非药材） | 输入闸门拒答，refuse_reason=**域外图**（补强宠物图 0.94 误判） |
| 候选 A（灰区） | none（都不像） | refuse_reason=**置信不足** + 补拍建议 |
| 任意 | 云端不可用（断网/超时/未配置） | **fail-soft**：跳过 VLM，回退本地结论；时间轴标注 `vision: skipped`；识别/图谱/对话全程可用（验收第 6 步不受影响） |

**合规设计（VLM 参与必须守住）**：
- 提示词限定：**仅从候选名单选择药材名 + 视觉理由，输出 JSON `{candidates: [...], verdict: "none"|"non_herb"}`**，绝不生成药性/功效/用量内容；
- 返回解析做**结构白名单校验**：只允许名单内药名 + none/non_herb 两种 verdict，含药性/功效文本一律丢弃；
- VLM 结果**不进知识问答路径**——它只影响"识别结论怎么呈现（提信/鉴别/拒答）"，知识回答仍由图谱 + 证据链闸门裁决。

**成本与降级**：仅灰区触发，预计 5%–20% 请求走云端；base64 前 PIL 压缩 ≤ 1.5MB；`VISION_TIMEOUT=5s` 超时即跳过；默认开关**关闭**（设置页手动开启）。

**独立配置（VISION 组）**：`VISION_API_URL / VISION_MODEL / VISION_API_KEY / VISION_TIMEOUT / VISION_ENABLED`，与聊天配置（DEEPSEEK 组）完全独立互不干扰；config.py 复用 `normalize_endpoint`；设置页新增"视觉验证（可选）"卡片（URL/Key/模型/开关/测试），app.py 新增 /api/vision-config 与 /api/vision-config/test。

## 九、合规、隐私与产品边界

### 9.1 合规要点（沿用立项报告 + 一期红线）

| 问题 | 项目要求 |
|---|---|
| 是否构成医疗器械 | 按预期用途/声明/部署场景判定；本项目定位辅助学习与知识查询，不做诊疗建议；若未来转向生产质检或临床，需重新评估 [7] |
| 是否面向公众 | 若对境内公众提供生成式服务，纳入《生成式人工智能服务管理暂行办法》治理要求 [6] |
| 患者/用户数据 | 最小化采集、脱敏、不留存个人健康信息；默认不用于训练 |
| 知识产权 | 图片（CC BY 4.0，NB-TCM-CHM）、药典条目、教材、论文逐一记录来源；**药典原文摘录限定在"事实性引注"范围** |
| 模型输出 | 高风险答案可追溯、可解释、可回滚（二期证据链 + 版本台账落点） |
| 医疗责任 | 一期文案/UI/接口已明确辅助决策边界，二期延续，不宣称替代专业人员 |

### 9.2 一期四红线（二期不变，写进子 Agent Prompt 与闸门）

1. **不输出诊断/辨证结论**——用户症状只作"知识查询线索"，不作病情判断；
2. **不输出具体剂量/疗效**——用量以知识条目展示（"药典记载"），不回答"你应该用多少"；
3. **不做真伪/产地判定**——素材市场真伪初筛场景明确不做；
4. **禁忌 = 知识展示**——十八反/十九畏双源展示（歌诀 + 药典认定），不是用药指导。

### 9.3 输出闸门 = 合规落点

五道闸门中的输出闸门是合规的法条落点：所有高风险建议附免责声明、证据来源、适用范围，支持人工复核与日志审计（一期免责面板已有，二期增加证据链条目明细）。

## 十四、立项决策建议

**建议结论：批准二期立项，采用"两步走"**（与立项报告一致，二期内容按本项目现状重排）。

| 阶段 | 项目定义 | 不做什么 |
|---|---|---|
| **二期：知识底座 + 智能体升级** | 60+ 味档案 + 药典原文（L1/L2）+ 版本台账 + 混合检索；任务型六子 Agent + 五道闸门 + 证据链拒识 | 不输出个体化处方；不诊断；不做真伪/产地判定；不重训识别模型 |
| **三期/远期：视觉侧 + 工程侧** | 类别扩充（20→100+，TCMP-300 增强候选）、主体定位框、图像质量检测、多图融合；用户角色、反馈闭环完整版、运营后台 | 仍需按具体场景做合规评估 |
| **远期：数智中药平台** | 产业链数据、质量追溯、智能质控、多端智能体、行业模型 | 按业务与监管条件逐步扩展 |

**立项成功关键（二期版）**：二期成败不在于"加了几个 Agent"，而在于**建立一套可核对、可版本化、可审计的中药知识台账，并把不确定性、安全和证据链写进每个子 Agent 的机制里**——这与一期"识别成功率"的成功标准完全不同，评价指标从"模型精度"转向"知识可靠 + 过程可控"。
